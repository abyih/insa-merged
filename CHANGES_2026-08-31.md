# PNTC — Changes Since Last Field Guide (2026-08-31)

This covers everything built and verified since the previous changelog (which ended
at the northbound RESTCONF TLS work). Each entry lists **Before → After → Purpose**,
plus a verification status:

- ✅ **VERIFIED** — tested against the live ODL/OVS/Mininet stack, ground truth confirmed
- ⚠️ **IMPLEMENTED, PARTIALLY VERIFIED** — code path exercised, but not every case proven live
- 🖥️ **UI ONLY** — renders correctly, not backed by real enforcement
- ❌ **NOT IMPLEMENTED** — discussed but not built

---

## 1. Path Trace — host+switch endpoints

**Before:** Path Trace only accepted host→host pairs; tracing "host to a specific switch"
wasn't possible.

**After:** Path Trace resolves either endpoint as a host or a raw switch (`openflow:N`),
using the existing topology graph and the same BFS pathfinding — no new pathfinding logic,
just endpoint resolution generalized in `src/utils/graph.js`.

**Purpose:** Lets you trace "from host 1 to switch 4" when debugging where a slice's
traffic actually terminates, without needing a host attached at every point of interest.

**Status:** ✅ VERIFIED — tested against live topology with mixed host/switch endpoint pairs.

## 2. Anomaly Detector ↔ Network Slicing closed-loop automation

**Before:** Anomaly Detector could flag a suspicious switch but had no connection to
Network Slicing — an operator had to manually cross-reference the alert, find the
attached host, and hand-build a quarantine slice.

**After:** `AnomalyDetector.jsx` now runs a real state machine per incident
(`DETECTED → MITIGATING → VERIFYING → MITIGATED/MITIGATION_FAILED → RECOVERED`):

- `resolveIdentity(switchId)` — reverse-resolves the real host attached to the alerting
  switch via `resolveSwitchHosts()` (new function in `graph.js`), and checks it against
  live slices from `useSlices()`.
- `runMitigation()` — on auto-mitigate (or manual "BLOCK" override), installs a
  **host-scoped** OpenFlow DROP rule via the existing `provisionSlice()` — fixed a bug
  where the port matched `"ANY"` (switch-wide), now matches the specific resolved port.
  Guards on `getActiveController() !== "odl"` and fails honestly (`MITIGATION_FAILED`)
  rather than pretending to succeed on ONOS, which doesn't support this path.
- Verification is a real `getFlows()` read-back against the controller, not a timer.
- If the alerting switch matches a real user slice, that slice's target gets
  `quarantined: true` (shown as a red badge in Network Slicing); otherwise a standalone
  `Auto-Isolated` slice is created — either way it's a real entry in `SliceContext`,
  not a UI-only flag.
- Recovery is log-only: once a previously-mitigated source reports NORMAL again, it's
  marked `RECOVERED` in the event log, but the DROP rule is **not** auto-removed —
  that still requires the existing manual rollback action.

**Purpose:** This was the core ask — detection alone doesn't stop an attack; this closes
the loop from "anomaly seen" to "attacker's traffic actually dropped at the switch,"
scoped to just that host so the rest of the slice/network keeps working.

**Status:** ⚠️ IMPLEMENTED, PARTIALLY VERIFIED — full ODL path tested end-to-end with a
real synthetic attack (flood → detected → host resolved → DROP flow installed → read-back
confirmed). ONOS path deliberately fails closed and is reported as such, not tested further
since it's out of scope by design.

## 3. Network Slicing — intent translation transparency

**Before:** "Parse & Auto-Fill Form" silently filled the slice form from a typed intent —
no visibility into what the parser actually keyed on.

**After:** New "Intent Translation" card shows, honestly:
- the raw **User Intent** text,
- **Matched Keywords** — the literal substrings the regex parser matched (via
  `collectMatchedKeywords()` in `intentParser.js`, which re-runs the exact same patterns
  the parser itself uses, so this can never drift from what was actually parsed),
  the compiled **Policy** (priority/latency/protocol/bandwidth/DSCP-queue/hosts).

**Fixed a real bug while doing this:** `parseHostHints`'s regex matched the bare letter
"h" inside ordinary words — e.g. "...traffic **wit​h** 20000 Kbps" was silently parsed as
phantom "host 20000". Fixed with word boundaries (`\b`) around the whole alternation.

**Purpose:** Directly answers "is this really NLP or just keyword matching?" — the UI now
shows its own regex matches, so it can't overclaim to be doing more than rule-based parsing.

**Status:** ✅ VERIFIED — confirmed live via the Hospital-Traffic preset; matched keywords
shown exactly match the parser's actual regex hits, phantom-host bug confirmed fixed.

## 4. Network Slicing — real enforcement verification panel

**Before:** A slice showing "Active" in the table meant only "the app's local state says
so" — no live check against the controller.

**After:** New "View Enforcement" button (per slice row) expands a panel that runs
`runVerifyEnforcement()`:
- `getFlows(switchId)` — confirms the classification rule actually exists on the device.
- `getQueueState()` / `getMeter()` — only checked when `latency === 'Low'` (i.e. only when
  a QoS policy was supposed to be provisioned), confirming the OVS queue/meter is real.
- Never shows a green check unless the live read confirms it — a slice with a missing
  flow or queue shows "NOT FULLY VERIFIED," not a fake pass.
- New checklist item, "Slice Enforcement Verified," only turns green when every target's
  verdict is `verified`.

**Purpose:** Same principle as #3 — make the dashboard's claims falsifiable against the
real controller state instead of trusting local app state.

**Status:** ✅ VERIFIED — live-tested submitting a real slice (HTTP, Low latency,
5000 Kbps) and confirming the panel reported the flow and queue as actually present on
the device.

## 5. Network Slicing → Flows integration

**Before:** No way to jump from a slice to see its actual flow entries.

**After:** New "View Flows" button navigates to `/flows` with the slice's flow name as a
filter (`location.state.filterFlowName`); Flows.jsx shows a filter banner ("Filtered to
flows matching X — N of M flows") with a Clear button.

**Fixed a real bug while doing this:** `Flows.jsx` was reading a dead localStorage key
(`active_sdn_controller`, from an unused old toggle component) to decide which controller
to query — meaning it could silently show the wrong controller's flows. Switched to the
actually-live `getActiveController()` from `controllerManager.js`.

**Purpose:** Closes the same "prove it, don't just claim it" gap — a slice's enforcement
claim should be one click away from the raw flow table.

**Status:** ✅ VERIFIED — clicked through live, confirmed URL, filter banner, and correct
single-flow result for a real submitted slice.

## 6. Egress-path QoS bug fix (the significant one)

**Before:** `PUT /api/qos/:switchId/:port` provisioned an OVS `linux-htb` queue only on
the **host-facing (ingress)** port of the given switch. HTB queues are strictly
**egress/TX-only** in OVS — queueing a host's ingress port does nothing to that host's own
outbound traffic, which actually egresses via a different (uplink/peer) port. In practice
this meant the configured QoS had **zero effect** on real traffic.

Also: no `max-rate` was ever set, only `min-rate` — meaning there was no actual rate
ceiling, just an unenforced floor guarantee.

**After:**
- New `listPeerPorts(bridge, excludeIface)` enumerates every other port on the same
  bridge — the real uplink/inter-switch ports.
- PUT now provisions the primary **and every peer port**; DELETE removes from all of them.
- `provisionQueueOnInterface()` now sets both `min-rate` and a real `max-rate`
  (2× min-rate, or falling back to the app's own existing `100_000` Kbps admission-control
  constant) — confirmed via `man ovs-vswitchd.conf.db` that both are in bit/s.

**Purpose:** This is the actual fix for the instructor's priority-queuing feedback —
without it, the whole DSCP/queue mechanism was cosmetic. Verified via
`ovs-ofctl queue-stats` that the previously-unconfigured uplink port now has a real queue.

**Status:** ✅ VERIFIED both statically (`ovs-ofctl dump-queues`/`queue-stats` before/after)
and dynamically — see the congestion test below.

## 7. Real congestion/latency test (proof the QoS fix does something under load)

**Before:** The egress-path fix (#6) was confirmed correctly *configured*, but never
proven to actually help real traffic under contention.

**Test:** Provisioned a 2000 Kbps priority queue on `openflow:1` (host 1's switch),
classification rule matching `ip-protocol=ICMP, ip-dscp=46, in-port=2 → queue 0`.
Generated a 700 Mbit/s UDP flood (h1→h4) to saturate the link, then sent 20 concurrent
pings marked DSCP 46 and 20 unmarked, both from h1, during the live flood.

**Real, measured result:**

| Metric | Marked (DSCP 46, queued) | Unmarked (best-effort) |
|---|---|---|
| Packet loss | 10% (2/20 dropped) | 25% (5/20 dropped) |
| Avg RTT | 3292 ms | 3322 ms |

**Honest interpretation:** the priority queue measurably **reduces packet loss**
(less than half, 10% vs 25%) under real congestion — it is doing real differentiated
scheduling, not a no-op. It does **not** meaningfully reduce latency at this
oversubscription level (~350× the queue's provisioned rate) — both classes sat around
3.3s RTT because the queue itself was full regardless of priority; priority only decided
who got dropped first, not how fast survivors moved. This is worth stating plainly rather
than overclaiming a clean win on both metrics.

**Purpose:** Directly answers the instructor's ask to "prove it with congestion tests and
measurements," with real numbers instead of a claim that the queue is configured.

**Status:** ✅ VERIFIED — real Mininet/OVS traffic, both `.log` files and `ovs-vsctl`/RESTCONF
confirmation. All test artifacts (queue, classification flow, iperf/ping processes) were
cleaned up afterward; confirmed the real slices (`Hospital-Traffic`, `AI-Intent-815`, etc.)
were untouched throughout.

## Known limitations carried forward (not fixed, reported honestly)

- **Persistence gap:** OVS QoS/queue rows can survive a Mininet rebuild as orphaned
  objects (zero port references) after the app's own reboot-recovery sequence, because
  nothing currently re-provisions QoS after infrastructure changes. Observed and cleaned
  up live during this session; not yet built as an auto-heal feature.
- **ONOS mitigation path:** the closed-loop auto-mitigation (#2) is ODL-only by design;
  on ONOS it fails closed (`MITIGATION_FAILED`) rather than silently no-op'ing.
- Recovery (#2) is log-only — a `RECOVERED` incident does not automatically remove its
  DROP rule; manual rollback is still required.
